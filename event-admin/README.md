# Event Admin (Project Loom Powered)

Легковесная, высокопроизводительная и потокобезопасная асинхронная шина событий внутри JVM, вдохновленная спецификацией OSGi Event Admin. Проект спроектирован специально для современных приложений на **Java 21 / 25** и полностью построен на базе **виртуальных потоков (Project Loom)**.

## 🚀 Ключевые возможности и архитектура

### 1. Виртуальные потоки из коробки (Project Loom)
В отличие от классических шин событий, использующих фиксированные пулы платформенных потоков (Thread Pools), `EventAdmin` выделяет под каждую задачу легковесный виртуальный поток. Это позволяет эффективно масштабировать систему до сотен тысяч параллельных событий, не блокируя потоки операционной системы при выполнении ввода-вывода (I/O) в подписчиках.

### 2. Изоляция ресурсов (Паттерн Bulkhead)
Шина защищена от проблемы «голодания ресурсов» (Thread Starvation), когда один медленный топик парализует работу всей системы. Внедрено двухэтапное квотирование на базе семафоров:
* **Глобальный лимит:** максимум 20 000 параллельных задач на всю шину для предотвращения утечек памяти (OOM).
* **Локальная квота топика:** максимум 1 000 параллельных задач на каждый корневой сегмент топика (например, всё, что начинается с `auth/` или `orders/`). Если один модуль зависает, другие продолжают работать на полной скорости.

### 3. Гарантированный FIFO-порядок по ключам (Routing Key)
Для бизнес-логики, критичной к последовательности выполнения шагов (например, `OrderCreated` -> `OrderPaid`), шина предоставляет встроенный механизм упорядочивания (подобие концепции Акторов или партиционирования в Kafka).
* Если у события задан `routingKey()`, оно попадает в изолированную последовательную очередь для этого ключа.
* Обработка внутри этой очереди идет строго один за другим. При этом сохраняются все преимущества Loom: если один шаг заблокируется на I/O, виртуальный поток припаркуется, не останавливая процессор.

### 4. Реактивная очистка памяти
Последовательные очереди по ключам (`routingKey`) создаются в памяти динамически и лениво. Как только все события по конкретному ключу обработаны и очередь пустеет, шина **атомарно удаляет внутренний процессор из памяти** через потокобезопасный контракт `ConcurrentHashMap.remove(key, value)`. Это полностью исключает утечки памяти (Memory Leaks) в долгоживущих приложениях при работе с миллионами уникальных ключей.

### 5. Безопасный API без проверяемых исключений
Интерфейсы спроектированы для максимальной лаконичности клиентского кода:
* Базовый интерфейс `EventAdmin` и токен подписки `Subscriber` переопределяют метод `close()`, убирая раздражающий `throws Exception`.
* Компонент можно безопасно использовать в блоках `try-with-resources` или вызывать `.close()` вручную без необходимости оборачивать код в шаблонные блоки `try-catch`.

## 🛠️ Структура интерфейсов

### Событие (`Event`)
Каждое событие должно реализовывать маркерный интерфейс `Event`. Рекомендуется использовать иерархическую структуру разделения через слэш (`/`).

```java
public record OrderEvent(long orderId, String status) implements Event {
    @Override
    public String topic() {
        return "app/orders/status-changed";
    }

    @Override
    public String routingKey() {
        // Все события по конкретному заказу обработаются строго друг за другом (FIFO)
        return "order-" + orderId; 
    }
}
```

### Подписка (`Subscriber`)
Метод `subscribe` возвращает токен управления жизненным циклом подписки.

```java
public interface Subscriber extends AutoCloseable {
    @Override
    void close(); // Не выбрасывает проверяемых исключений!
}
```

## 💻 Примеры использования

### Создание шины событий

```java
// Вариант 1: Со стандартным выводом ошибок в System.err
EventAdmin eventAdmin = EventAdmin.create();

// Вариант 2: С централизованной кастомной стратегией логирования ошибок бизнес-логики
EventAdmin eventAdmin = EventAdmin.create((event, throwable, listenerName) -> {
    logger.error("Ошибка в подписчике '{}' на топике '{}': {}", 
        listenerName, event.topic(), throwable.getMessage());
});
```

### Подписка на события (Точное совпадение и Wildcard)

```java
// 1. Точное совпадение топика
Subscriber exactSub = eventAdmin.subscribe("app/orders/status-changed", OrderEvent.class, event -> {
    System.out.println("Статус заказа изменился: " + event.status());
});

// 2. Использование Wildcard (подписка на все подтопики модуля 'app/orders/')
Subscriber wildcardSub = eventAdmin.subscribe("app/orders/*", OrderEvent.class, event -> {
    System.out.println("Логирование любого события модуля заказов: " + event.topic());
});
```

### Отправка событий (Fire-and-Forget)

Метод `postEvent` полностью асинхронный. Он мгновенно возвращает управление продюсеру, делегируя обработку виртуальным потокам ядра. В случае, если шина закрыта или критически перегружена, метод выбросит `IllegalStateException`.

```java
try {
    eventAdmin.postEvent(new OrderEvent(12345L, "PAID"));
} catch (IllegalStateException e) {
    // Обработка ситуации, когда шина завершает свою работу
}
```

### Отмена подписки и закрытие шины

```java
// Отмена конкретной подписки
exactSub.close(); 

// Глобальное вежливое завершение работы шины (Graceful Shutdown)
// Мгновенно блокирует новые публикации, очищает ссылки для GC и ожидает завершения активных задач до 5 секунд
eventAdmin.close(); 
```

## 🛡️ Безопасность при закрытии (Lifecycle)
Компонент спроектирован с учетом экстремальных граничных случаев:
* Если поток-продюсер вызывает `postEvent` ровно в микросекунду закрытия пула, шина перехватит внутреннее системное исключение `RejectedExecutionException`, **гарантированно освободит занятые квоты (семафоры)** и выбросит понятный `IllegalStateException`.
* Повторные вызовы `close()`, а также вызовы `Subscriber.close()` после закрытия всей шины являются полностью **идемпотентными** и безопасными (не генерируют `NullPointerException`).
